**Timestamp source: file mtime.**  A per-step `ts` field exists in
only part of the corpus (it is absent from every step of the older
transcripts), and the epoch suffix of a run id is a dispatch stamp,
not a wall clock, so neither can date a run on its own.  File mtime
is present for every transcript, so the window is applied on mtime
for all runs.  The window end is the newest transcript mtime in
the corpus, so the slice is the last days *of the corpus* and a
frozen corpus still yields a full 14-day slice,
reproducibly.

**Definitions.**

* *final tokens_in* -- `tokens_in` of the last step of the run: the
  final prompt the worker was billed for.
* *end-to-end tokens_in* -- sum of `tokens_in` over all steps of the
  run: the whole prompt bill of the run.
* *tool-result chars* -- characters of the `tool_results` text,
  paired by index with the `tool_calls` of the same step and
  classified as exec / read_file / list_dir / other.
* *tool-output share* -- (tool-result chars / 4) / final tokens_in,
  i.e. the estimated share of the final context that is tool output.
* *truncation-cap hits* -- number of `...[truncated]` markers in
  tool results (the harness output cap already fired).
* *ceiling saving* -- for every step, the tool-output tokens
  injected into the context before that step, times the compression
  level, capped at the step's own `tokens_in`; summed over the run.
  This is the maximum plausible end-to-end `tokens_in` saving of
  compressing the measured slice; it assumes no other growth.
